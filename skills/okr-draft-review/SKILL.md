# OKR 起草与检查

根据用户的组织规则和原始意图工作。区分 Objective（希望发生的变化）、Key Result（验证变化的结果）和 Initiative（为实现结果而做的行动）。不要把完成任务直接当作结果，除非用户的场景确实以交付物作为可验证成果。

## 先确认背景

从用户提供的材料中提取周期、适用范围、上级目标或战略、现状与基线、指标口径、可用数据源、负责人和资源约束。已有文档优先于通用范式。缺失的信息若影响目标方向或指标定义，提出少量关键问题；可以先推进的部分写明假设，并把未知数据标为“待确认”。不要编造基线、目标值、负责人或数据来源。

## 起草模式

1. 先写少量聚焦的 Objective。每个 Objective 应说明希望改善的状态及其价值，避免只列工作项目。
2. 为每个 Objective 设计足以判断其是否达成的 KR。尽量写明指标名称及口径、基线、目标值、截止时间、负责人和数据来源。定性 KR 应事先定义可核验的验收标准。
3. 检查 KR 组合能否共同支撑 Objective，是否重复计数，以及负责人是否有合理的影响力。把行动建议放在单独的 Initiative 栏，不混入 KR。
4. 不强制固定 O 或 KR 的数量，也不默认某个评分尺度；优先遵循用户或组织已有的规则。

## 检查模式

逐条保留原文，并按以下维度指出具体问题：目标是否聚焦且有意义；KR 是否衡量结果；基线、目标、期限与取数口径是否清楚；是否能归因或至少受到负责人影响；KR 之间是否重复、冲突或遗漏；与上级目标是否对齐。将问题标为“必须修正”或“建议改进”，说明理由，并给出尽量保留原意的改写。没有问题的条目说明其可保留的原因。不要为使表格完整而擅自补数字。

## 输出

- 起草：先展示 O/KR 草案，再列待确认数据与假设；需要时附上独立的 Initiative 建议。
- 检查：用“原文｜判断与理由｜建议改写”逐条呈现，最后总结最影响质量的 1–3 个问题和需要用户确认的信息。
- 用户要求评分或复盘时，先确认其既定评分规则和实际数据。依据证据计算或判断，并区分“未达成”和“数据不足”；没有规则时先提出可供确认的评分口径。

仅在用户要求保存、导出或更新时写入文件或外部系统。
